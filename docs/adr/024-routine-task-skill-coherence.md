# ADR-024: Routine/recurring-task ↔ skill coherence — the task defers to the governing skill

## Status

Accepted

## Date

2026-07-04

## Context

A live deployment surfaced a defect: a generated **routine task** and the
**skill** it drives each specified the same process independently, and they diverged. The
task restated a looser version of the skill's storage shape, output format, and source
scope. At runtime a Paperclip agent follows the routine/recurring **task** as its wake
instruction, with the attached skill as supporting context — so when the two disagree, the
task wins. The produced output violated the skill: wrong storage, wrong note format,
missing sections, off-spec sources.

Root cause: routine/recurring-task text and skills are generated by **separate prompts with
no coherence constraint**. The `task_generator` prompt never saw the assignee's skills and
had no instruction to defer, so it freely authored a full "how" — format, storage protocol,
step-by-step — that could (and did) contradict the skill that actually governs the work.

## Decision

Encode the principle: **when a routine (or its recurring task) drives work that an attached
skill governs, the generated task must be thin and deferential.** The skill is the single
source of truth for *how* (output/format, storage/naming protocol, step-by-step procedure,
source scope); the task carries only *when* (trigger/schedule) + *what-this-run* (scope) +
*which skill* (an explicit reference: "perform &lt;work&gt; per the `&lt;skill&gt;` skill;
produce its prescribed output, format, and storage"). The task must not restate the skill's
format, storage protocol, step-by-step process, or source scope.

Three changes implement it:

1. **Prompt (`task_generator.md`).** The prompt now receives the assignee's attached skills
   and an `is_recurring` flag, and instructs deference: if an attached skill governs the
   work, name it and defer the how to it; do not duplicate its format/storage/protocol.
   Where an attached skill's remit matches the task, the task should name it.

2. **Wiring (`generate_task` / `bundle.py`).** `generate_task` takes `assignee_skills` and
   threads the slugs into the prompt; the full pipeline passes each task's assignee's skill
   list (built from the planned org, so reportsTo/skill assignment is already fixed).

3. **Advisory validator (`renderers/render.py::_routine_skill_incoherence`).** A lightweight
   heuristic, surfaced via the existing `warn` sink (NEVER a validation error, mirroring the
   `_routine_cadence_smells` pattern): for each recurring task, if its objective/criteria
   restate concrete format/storage tokens (`markdown`, `directory`, `headings`, `table`, …)
   that a co-attached skill also defines, warn — naming the task, the skill, and the shared
   tokens. Meta-words (`format`, `storage`, `protocol`) are deliberately excluded so the
   recommended deferential phrasing does not trip it.

## Consequences

### Positive consequences
- A generated recurring task can no longer silently contradict the skill it invokes; the
  skill stays the single source of truth for the how.
- The deployment defect (task overriding skill at runtime) is addressed at generation time.
- The advisory warning gives the operator a cheap signal when a task drifts back toward
  restating a skill's protocol.

### Negative consequences
- The deference is prompt-enforced, so it is best-effort, not guaranteed — hence the
  advisory heuristic as a backstop rather than a hard gate.
- The heuristic is token-overlap based: it can miss a paraphrased restatement (false
  negative) or flag an incidental shared word (false positive). It is advisory, so both are
  tolerable.

### Neutral consequences
- Non-recurring tasks are not flagged by the heuristic (the defect is specific to
  schedule-driven wakes where the task is the standing instruction), though the prompt's
  deference guidance applies to any skill-governed task.
- Built-in catalog skills (ADR-023) have no `SKILL.md`; the heuristic simply skips them (no
  local text to compare), which is correct — they are not the domain-process governor.

## Alternatives considered

- **Make incoherence a hard validation error.** Rejected: the match is heuristic; a false
  positive must not block a bundle. A warning lets the operator judge.
- **Generate the task from the skill (single prompt).** Rejected as too large for this fix:
  it couples task and skill generation and reshapes the fan-out. Deference + an advisory
  check solves the observed defect without that restructuring; can be revisited if drift
  persists.
- **Strip all "how" language from every task unconditionally.** Rejected: a task with no
  governing skill legitimately carries its own concrete criteria; deference applies only
  when a skill governs the work.
